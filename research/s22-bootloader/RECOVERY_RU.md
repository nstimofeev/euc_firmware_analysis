# S22: обновление и восстановление после неудачной прошивки

2026-10-11. Исследован **исторический загрузчик `20220406`** из закреплённого публичного SWD-дампа. Его совпадение с загрузчиком конкретного колеса и поздних плат не установлено. Входы и хеши — [intake.json](intake.json); происхождение — [первый отчёт](REPORT_RU.md).

**Механизм восстановления — сохранённый загрузчик и повторная передача приложения целиком. Резервной рабочей прошивки, переключения A/B и автоматического отката в восстановленных путях нет.** Основное приложение стирается и записывается по месту. Найдены два существенных ограничения: окно стирания до фиксации маркера и пропущенная инициализация приёмника при повреждённом приложении без маркера. Sentinel-дескриптор позволяет запустить тело без проверки его суммы.

## Доступный код и разметка

| Адрес | Назначение |
|---|---|
| `08000000`, reset `080001cc`, main `08002b2c` | Основной загрузчик, старый поток приёма с AES |
| `08004000`, reset `080041ec`, main `080043d6` | Самостоятельный дополнительный обновлятор с другим протоколом; **не резервное приложение** |
| `08008000` | Единственный исследованный слот основного приложения |
| `0803d000 = 55aaaa55` | Постоянный маркер основного режима обновления |
| `0803d800 = 28635690` | Выбор дополнительного обновлятора в ветке нормального запуска |

Reset основного образа вызывает настройку системы `0800179c`, затем CRT `08000130` и main. Инициализированные данные копируются из `08003198` в `20000000` (204 байта); BSS — `200000cc..20000e70`. Второй образ имеет собственный CRT и RAM до `200024d0`.

Сохранены [автоматический C Ghidra](automatic_decompilation.c) и [адресованный дизассемблер](recovery-code.asm). C — восстановленный псевдокод, а не исходники производителя; типы, возвраты и распознавание функций могут быть ошибочными. Существенные выводы ниже проверены оригинальными ARM-инструкциями.

## Основной загрузчик: приём → запись → запуск

В `08002b2c` аппаратная подготовка приёмника выполняется, если маркер `0803d000` установлен **или** функция аппаратного входа `08000b88` возвращает 7. Затем активный режим обновления включается при маркере **или** результате 0 из проверки приложения `0800278c`. Это два разных условия; именно их несовпадение создаёт проблему восстановления без маркера.

`08000b88` читает три GPIO по базе `40011000`, маски `40/80/100`, и SPI-значение через `08002d74`; при определённом отрицательном значении и флаге варианта также возвращает 7. Конкретный безопасный физический жест, положение колеса или последовательность нажатий, обеспечивающие этот вход, не установлены. В тестах заменён **только результат аппаратного опроса**, а не ветвление загрузчика.

Восстановленный основной поток:

1. `08002334` — автомат приёма; `08001454` проверяет кадр. Рабочий исследованный кадр: `01`, однобайтный номер, **16 байт** полезных данных, CRC-16 big-endian. Полином `1021`, начальное значение 0. Это изменённый SOH/YMODEM-подобный протокол, не стандартный 128-байтный YMODEM. Дубликат подтверждается без повторной записи; неверный CRC получает NAK.
2. Заголовок содержит имя, NUL, десятичный размер и пробел. `08000844` обнуляет CBC IV, вызывает оригинальную подготовку AES `080026ec` и стирает страницы приложения через `08002868`. Размер сравнивается с выражением, использующим аппаратный halfword `1ffff7e0`; выбранное в эмуляции значение не измеряет ёмкость реального MCU.
3. Для каждого принятого блока `08002758` исполняет **AES-256-CBC** с цепочкой предыдущего шифротекста. Ключ находится в инициализированных данных образа; режим и цепочка независимо сверены с cryptography на четырёх блоках. `080028ba` пишет расшифрованные слова прямо от `08008000`, адрес увеличивается на длину данных. Страницы — `800` байт.
4. Завершение использует два EOT и пустой заголовок. Проверяется накопленный XOR CRC принятых кадров, но значение ожидаемой суммы **0 явно допускается**. После результата 4 main вызывает `0800278c`; результат 1 разрешает выход из обновления и переход по вектору приложения. Перед этим вызывается `08000bf4(4,ad9)`: записи в регистры `40003000` с ключами `5555/aaaa/cccc` соответствуют настройке независимого watchdog. Реальная длительность и сброс watchdog не эмулировались.

В парсере есть ветка STX с заявленными 1024 байтами, но локальный буфер автомата и основной кольцевой приёмник имеют по 256 байт. Работоспособность большого кадра этим загрузчиком не подтверждена; она не следует из наличия этой ветки или из изменений DMA в позднем приложении.

Сквозной тест оригинального main, а не только отдельного валидатора, проверяет шесть вариантов синтетического 1024-байтного тела: обычный корректный дескриптор, неверную сумму, sentinel, неверное арифметическое соотношение и две ошибки flash-записи. Цель перехода перехватывается до исполнения синтетического приложения; установочный образ не сохраняется.

## Что именно проверяется перед запуском

`0800278c` читает версию по `08008308` (порог `20211027`) и поля `08008310..0800831c`:

- При обычном `RUNOKFLG=ffffffff` и правильном соотношении `APPSIZE + APPCRCCODE + 14502367 = APPCRCCHECK` суммирует LE uint32 тела от `08008320`. Порог APPSIZE — `32800`. Неверная сумма даёт 0 и оставляет основной поток в обновлении.
- При `RUNOKFLG=APPCRCCHECK` возвращает 1 **без чтения тела**. Официальное приложение S22 2.41 имеет именно такие поля: `268479df`, size=0, code=`12345678`.
- Если арифметическое соотношение нарушено, тоже возвращает 1. Сквозной тест подтвердил, что вызывающий main трактует этот результат как разрешение выйти к приложению.

В исследованном **основном потоке** после приёма/дешифрования нет дополнительной проверки цифровой подписи перед переходом: путь замыкается на этих проверках и проверке стартового SP маской `2ffe0000`. Это вывод из восстановленного потока управления и его исполнения, а не из самого факта наличия CRC/AES. Он не переносится на поздние загрузчики, дополнительный обновлятор в целом или реальное принятие модифицированной прошивки колесом.

Ошибки обработки flash дополнительно ослабляют гарантии: writer обнаруживает несовпадение прочитанного слова и возвращает 2, но `08002334` игнорирует возврат, передвигает адрес и посылает ACK. Ошибка стирания также не отменяет принятие заголовка. Сквозной тест с потерянной записью слова тела оставляет обычный дескриптор в режиме обновления, но sentinel позволяет перейти к приложению. Объявленный размер тоже не ограничивает непосредственно ветку записи данных: в ограниченном тесте с заявленными 16 байтами приняты 32; большой выход за разделы не моделировался.

## Восстановление и границы гарантии

| Ситуация | Поведение исходного кода | Практический смысл |
|---|---|---|
| Повреждён отдельный пакет | NAK; повтор принят. Дубликат ACK без второй записи и без сдвига CBC | Возможен повтор пакета в текущем сеансе |
| Питание пропало во время записи, маркер уже установлен | После свежей RAM main видит `55aaaa55`, готовит приёмник и остаётся в обновлении | Повторная передача всего файла; новая попытка снова стирает от `08008000` |
| Передача закончилась, питание пропало до очистки маркера приложением | Даже корректное приложение при установленном маркере остаётся в приёмнике после перезапуска | Автоматического запуска только по корректному телу здесь нет; доступен повтор обновления |
| Питание пропало после стирания приложения, **до записи маркера** | Приложение уже FF, маркера ещё нет; main включает RAM-флаг обновления, но **не выполняет RX-init** при аппаратном условии !=7 | Повторная передача через обычный транспорт после одного перезапуска не гарантируется |
| Повреждённое приложение без маркера | То же несовпадение условий; auxiliary-маркер не исправляет его, если обычный checksum-путь даёт 0 | Код загрузчика сохранён, но автоматический вход в рабочий приёмник неполон |
| Тело принято по sentinel или приложение запускается, но падает | Проверка тела пропущена; нет восстановленного выбора старой копии по неудачному запуску | Watchdog/reset сами по себе не обеспечивают откат |
| Повреждён сам основной загрузчик | Этот механизм уже не может исполниться | Восстановление внешним доступом требует отдельной проверки MCU, SWD/ROM-режима и конкретной платы |

**Окно до маркера подтверждено исполнением:** в обработчике заголовка `08000844 → 08002868` стирается приложение; только после возврата результата 2 main в `08002c18..08002c38` стирает `0803d000` и пишет `55aaaa55`. При остановке в `08002c0e` после принятого заголовка приложение уже FF, маркер ещё FF. Свежий запуск с таким flash-снимком пропускает RX-init; синтетическое аппаратное условие 7 возвращает настройку приёмника. Если маркер выставлен приложением заранее, это окно для данного сеанса отсутствует. Все пути фактического запроса обновления в позднем приложении пока не сопоставлены.

При повторном приёме загрузчик начинает с первого адреса приложения. В исследованном потоке нет сохранённой во flash позиции продолжения, копии предыдущего приложения или атомарного переключения двух слотов. В успешных сквозных тестах первые 32 КиБ остаются неизменными. Это проверка обычного ограниченного обновления, а не доказательство невозможности любой ошибочной записи за границы.

В оригинальном приложении **2.41** `08019dd8` первым вызовом запускает `0801ff5c`, которая стирает страницу `0803d000`, если слово не FF. Оригинальный код этой процедуры также исполнен: маркер очищен. Эта очистка находится в инициализации, не в подтверждении длительной исправной работы. Поэтому наличие watchdog не означает trial boot, проверку здоровья новой версии или автоматический rollback.

## Зачем второй образ

Дополнительный образ — другой обновлятор. `08004a12` разбирает поток `55 AA`, длину и CRC; `08005326` обрабатывает D0/D1. D1 принимает до 32 байт открытых данных с номером, собирает страницу в RAM от `200000c0`, а при заполнении пишет приложение страницами по `800` байт; D0/1 дописывает неполную страницу, D0/2 меняет флаг завершения. Исходный разбор кадра, очереди, обработчик и запись 32 открытых байт проверены вместе. В этой ветке данные не проходят первичный AES-дешифратор.

Маркер `0803d800` устанавливается `08004962`, стирается `08004978`; оба helper проверены оригинальным кодом. Основной загрузчик выбирает второй образ только в ветке нормального запуска, после первичного решения по приложению. Поэтому он не является независимой гарантированной аварийной копией для любого повреждения.

Есть дополнительные ограничения: `08004804` требует halfword `1ffff7e0 = 100` и проверяет связь с аппаратными словами от `1ffff7e8`. Первый запуск через callback `080047c8` записывает поля **самого второго образа** `08005304/08005300`; повторный запуск проверяет эту связь. `08004872` также проверяет прикладное поле `08008304`, если не установлен флаг первого запуска. На синтетическом UID проверены привязка, повторный старт, остановка при другом UID и отказ/разрешение по полю приложения. Это простая аппаратная привязка; реальные значения MCU пользователя неизвестны. Полный сценарий штатного клиента и завершения второго протокола на конкретном колесе не установлен.

## Что это даёт для дальнейшей работы

Теперь есть достаточный код для разработки офлайн-модели старого протокола и проверки отдельных механизмов восстановления. Утверждать «любую неудачную прошивку можно исправить через Bluetooth» нельзя: нужны совпадение загрузчика, рабочий вход в приёмник, связь с BLE-модулем и штатным клиентом. Внешний SWD-доступ подтверждён происхождением дампа одного S22, но не проверен на плате пользователя; процедура ROM-восстановления и состояние защиты чтения для неё неизвестны.

Отдельно не следует смешивать маркеры: позднее приложение 2.41 пишет `28536692` по `0803a800` в `08023530` перед одной из веток сброса. В исследованном main загрузчика используются `0803d000/0803d800`. Приложение само читает `0803a800` в `08009d6c`. Семантика этой команды относительно данного старого загрузчика и фактический путь запроса OTA в текущем колесе остаются отдельной задачей.

## Воспроизведение

Из корня репозитория после установки requirements.txt:

```sh
python research/s22-bootloader/inspect_bootloader.py
python research/s22-bootloader/trace_recovery.py
```

Второй скрипт использует закреплённые загрузчик и приложение 2.41. Проверяет старт, первичный AES/CRC/повторы, шесть сквозных решений main, ошибки стирания/записи, snapshots после обрыва, очистку маркера приложением и framed-приём дополнительного образа. Результаты — [recovery-evidence.json](recovery-evidence.json). Свежая RAM при перезапуске задаётся как CRT copy+BSS; физическое отключение питания, прерывания, UART/BLE, watchdog и электрические сбои FMC не моделируются. Контроллер flash заменён явно указанными driver-boundaries; оригинальные erase/write loops, проверки и main продолжают исполняться. Никаких пакетов колесу не отправлялось.

Для C использованы Ghidra 10.4 и JDK 17, raw import `ARM:LE:32:Cortex`, base `08000000`, затем [SeedBoot.java](SeedBoot.java) и [ExportBoot.java](ExportBoot.java). Пример:

```sh
analyzeHeadless /tmp/s22-ghidra boot -import research/s22-bootloader/S22-boot-area-20220406.bin \
  -loader BinaryLoader -loader-baseAddr 0x08000000 -processor ARM:LE:32:Cortex \
  -scriptPath research/s22-bootloader -preScript SeedBoot.java \
  -postScript ExportBoot.java /tmp/s22-boot.c -max-cpu 2
```

Экспорт автоматический, и повторные проходы Ghidra могут по-другому выделить функции. Доказательства поведения — закреплённые бинарники, адреса и скрипты исполнения.
