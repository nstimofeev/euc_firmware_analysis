# Доступность загрузчика S22 и первый проверенный срез

**Этот текст сохраняет границу доказательств первого среза. Продолжение выполнено:** [основной поток обновления, второй обновлятор и восстановление после сбоя](RECOVERY_RU.md). Условия запуска из main, AES, повтор передачи, ошибки flash и перезапуски теперь проверены оригинальным кодом; экспорт C также сохранён. Перечисленные ниже неизвестные относятся к моменту первого среза, кроме соответствия конкретной плате и аппаратных испытаний.

2026-10-11. **Код загрузчика S22 теперь доступен для офлайн-разбора.** Ранее в репозитории были приложения и сравнительный загрузчик KS-XE; заявления старых отчётов об отсутствии дампа S22 относятся к тому набору входов и теперь устарели.

## Откуда код

Публичный проект [jeremy-prater/ks-s22-mods](https://github.com/jeremy-prater/ks-s22-mods/tree/9258eac039304991a815b8880c4dddca7a4e983c) содержит `firmware/capture.bin` на 512 КиБ. Автор описывает считывание S22 через SWD/OpenOCD. Исходный SHA-256, URL и извлечение записаны в intake.json. Здесь сохранены только первые **32 КиБ** (`08000000–08008000`), достаточные для изучения найденных образов перед приложением. Это исходные байты, не реконструкция из другого колеса, не исходники и не дамп текущего колеса пользователя.

В `08001300` лежит строка `BootSoftVersion-Date-20220406-Model-KS-S22----CPUTYPE_0`. Она прямо идентифицирует S22 и дату в версии загрузчика. CPUTYPE_0 не расшифровывается здесь как конкретная модель MCU.

| Вход | Что установлено |
|---|---|
| `08000000`: SP=`20000e70`, reset=`080001cd` | Вектор и исполняемый ARM Thumb код основного загрузчика |
| `08004000`: SP=`200024d0`, reset=`080041ed` | Второй самостоятельный образ в области перед приложением; полное назначение пока не восстановлено |
| `08008000` | Начало основного приложения в полном дампе |

32 КиБ — извлечённая область, не размер сплошного кода загрузчика: внутри есть FF-промежутки и второй образ. Код читается и дизассемблируется без расшифровки OTA-файла. Полного ручного разбора, экспортированного C/Ghidra-проекта и аппаратной проверки ещё нет.

## Что удалось проверить в оригинальных инструкциях

1. Локальная ветка `08002ca4` проверяет слово `0803d800` на `28635690`. Если оно совпадает и стартовый SP второго образа проходит маску `2ffe0000`, код вызывает подготовительные функции, загружает MSP и переход по reset vector второго образа `08004000`. Иначе проверяет SP приложения по той же маске и аналогично переходит на `08008000`. Три ограниченных прогона подтвердили выбор адресов и смену SP; подготовительные функции заменены заглушками. **Это только ветка внутри главного цикла, не полная эмуляция старта и не политика допуска OTA.**
2. Функция `0800278c` читает прикладные поля `08008308–0800831c`. Есть арифметическое соотношение `APPSIZE + APPCRCCODE + 14502367`, ветка суммирования LE uint32 тела по `08008320`, порог APPSIZE `32800` и отдельные ранние возвраты. Проверено исполнением оригинального кода на восьми синтетических дескрипторах.
3. Для sentinel-дескриптора (`RUNOKFLG=APPCRCCHECK=268479df`, size=0, code=12345678) функция возвращает R0=1 и **не читает тело**. Изменение тела этого результата не меняет. Но R0=1 также бывает при нарушенном арифметическом соотношении, поэтому название «валидатор» и трактовка «R0=1 означает принятие прошивки» без разбора вызывающих веток некорректны. На обычном дескрипторе с RUNOKFLG=ffffffff совпадающая сумма даёт 1, несовпадающая — 0; полный поток использования результата не исследован.
4. В процедуре `08000844`, участок `080008ac–080008c2`, есть чтение halfword аппаратного адреса `1ffff7e0` и вычисление границы `08000000 + value*2048 - 08008000` для сравнения с длиной. Само значение аппаратного регистра в SWD-файле отсутствует; оно не разрешает прежнюю неопределённость о ёмкости MCU. Весь обработчик передачи здесь не исполнялся.

## Что ещё неизвестно

- Полный протокол приема основного OTA, дешифрование именно этим загрузчиком, все границы flash-записи и условия завершения обновления.
- Все пути проверки образа, возможная криптографическая подпись и политика версий. Найденная сумма не доказывает отсутствие другой проверки.
- Назначение второго образа и его роль при обновлении/восстановлении.
- Совпадение этого загрузчика с колесом пользователя и поздними ревизиями/выпусками. Дата в строке ранняя; устанавливать соответствие по версии приложения нельзя.
- Запись или обновление самого загрузчика через BLE; код этого ещё не установлен. Наличие SWD-дампа другого владельца не доказывает доступность SWD на любой плате.
- Принятие модифицированного приложения на реальном устройстве. Ничего устройству не отправлялось; установочные образы не создавались.

Практический следующий шаг теперь возможен без разборки колеса: проследить reset → главный цикл, потребителей `0800278c`, приём данных → дешифрование → flash → завершение. Историческая необходимость «сначала добыть загрузчик S22» снята для первого офлайн-разбора.

## Проверка

Из корня: `python research/s22-bootloader/inspect_bootloader.py` (capstone/unicorn из requirements.txt). Воспроизведение извлечения из исходного файла: добавить `--capture /path/to/capture.bin`. Скрипт проверяет хеши, идентификационную строку, 8 случаев дескриптора, 3 локальных перехода; пишет evidence.json и selected-code.asm. Байты flash/маркеры меняются только в памяти эмулятора; сохранённый входной бинарник не модифицируется.
