# Автомат зарядки S22 2.37 и 2.41: первый завершённый срез

Состояние — байт `0x2000066c`; диспетчер 2.37 `0x0801b45c–0x0801b47d` (`tbb` в `0x0801b464`), 2.41 `0x0801ba38–0x0801ba59` (`tbb` в `0x0801ba40`). Байты таблицы переходов и все 21 цель для каждого образа сохранены в `transitions.json`. Здесь «запись на GPIO» означает только наблюдаемую запись по адресу MMIO с инертной моделью памяти; назначение электрической цепи неизвестно. Помощники `0x0800baf2`/`0x0800baee` в 2.37 и `0x0800bcda`/`0x0800bcd6` в 2.41 записывают маску 2 соответственно по `0x40011010`/`0x40011014`; также встречается запись 1 по bit-band адресу `0x422101b0`.

## Таблица 2.37

В таблице `C` — число **вызовов автомата при выполнении условия**, а не секунды. Если условие перестало выполняться, указанные счётчики часто уменьшаются, а не сбрасываются. Последовательность проверок состояния 2 имеет значение: первая успешная ветка 2→6, 2→3, 2→4 или 2→8 сразу уходит в общий хвост; два поздних условия 2→9 проверяются последовательно и не прекращают тот же вызов. Кроме того, входной блок исполняется **до** диспетчера, поэтому при 2→5 за один вызов выбирается уже состояние 5.

| Текущее состояние и адрес ветки | Условие, счётчик и следующий state | Записи при переходе |
|---|---|---|
| Любое → 5, `0x0801b3b4–0x0801b452` | Если `0x20000648=1` и state=2, вычисляется `0x20000646=(ADC[0x200034fe]>>4 - zero[0x2000064a])*17` с сохранением в signed halfword. При результате >12000 `0x20000660` нарастает до 50; когда **старое** значение ≥50, state=5. Иначе при счётчике >10 он уменьшается на 1, при ≤10 очищается флаг `0x20000672`. | `0x422101b0←1`, вызов set-помощника, `0x20000672←1`, `0x20000675` увеличивается до 10. При `0x20000648≠1` этот блок не выполняет указанную проверку тока. |
| 0, `0x0801b47e–0x0801b498` | `0x20000690` (u16) увеличивается, пока старое значение <50; затем 0→1. | Только state; нет MMIO в ветке. |
| 1, `0x0801b49a–0x0801b518` | `0x20000698` (u8) увеличивается. Новое значение <20: ветка записи. 20–39: прибавление `ADC[0x200034fe]>>4` в u32 `0x20000694` (20 отсчётов). Далее отдельная логика без изменения charge state может записать **0** по `0x422101b0`, если `0x2000069c≠1`, `BatState=0`, `diag_cartstep=0`, счётчики отсутствия батареи и низкой скорости достигли своих порогов (`0x0801ba92–0x0801bb6e`). Вышеуказанные MMIO-записи переходов поэтому не исчерпывают все записи за полный вызов функции.

## Сопоставление 2.41 и более ранних версий

В 2.41 функция `0x0801b990`, диспетчер `0x0801ba40`; состояния 0/1/20 начинаются в `0x0801ba5a/0x0801ba76/0x0801baf6`, состояние 2 в `0x0801bb44`, проверки Age/Voltage/Current в `0x0801bbb0/0x0801bc14/0x0801bc84/0x0801bce8`, две поздние ветки 2→9 в `0x0801bd6a/0x0801be36`, общее восстановление в `0x0801bea2`, состояние 6 в `0x0801bf26`, общий хвост в `0x0801bf8a`. Пороги, записи в charge-state RAM и порядок перечисленных веток совпадают в просмотренных инструкциях. Существенное адресное отличие входов: BMS-биты находятся по `0x20005101`/`0x20005409` (в 2.37 `0x20004d39`/`0x20004ef9`); два поздних счётчика берут входы `0x2000315a/5b` вместо `0x20003158/59`. Помощники MMIO имеют другие адреса, указанные выше. Это не утверждение о полном тождестве поведения всех вызовов функции.

Исследование 2.22/2.23 касалось **аналогичной ветки раннего нуля**, но там state был `0x2000065c`, счётчик `0x20000684`, ADC `0x200034a6` (`research/charge-early/REPORT_RU.md`). Здесь такие адреса в 2.37/2.41 относятся к другим полям; числовой state=1, диапазон 1082…3246, схема 20 сложений и типы MMIO-записей соответствуют, а прямое адресное отождествление RAM неверно. Исследование `research/units-timing/REPORT_RU.md` уже проверило state20 2.37: цикл `0x08009ea8→0x0802479c→0x0801b3b4` и ожидание `0x0800dca8(...,100,...)`. Здесь уточнены соседние переходы и порядок проверок. Из тайм-аута ожидания нельзя вывести безусловную длительность в секундах: ранние пробуждения и изменения событийного состояния меняют число фактических вызовов.

## Проверка и границы

`emulate_transitions.py` исполняет непосредственно оригинальный Thumb из двух образов с инициализированной RAM и инертной MMIO, останавливаясь перед общим хвостом. Восемь случаев (по четыре на версию) проверили 0→1 при старом счётчике 50; 1→2 при среднем 1000 с `zero status=2`; 2→6 при старом счётчике 100; 6→2 при старом счётчике 100. JSON хранит значения RAM и конкретные наблюдаемые MMIO-записи с PC. Дополнительно 21-элементная таблица переходов декодирована из исходных байтов `tbb`, с SHA-256 обоих входов. Команда из корня репозитория:

```bash
python research/charge-states/emulate_transitions.py
```

Непосредственно не эмулированы пороговые ветки 2→3/4/8/9/5 и общий хвост вместе с его параллельными пишущими путями. Их условия приведены по disassembly и сопоставленному псевдокоду, а не как результат отдельного теста. В частности, переход 2→20 может быть перезаписан поздней проверкой в том же вызове. Не определены физическое назначение MMIO-адресов, фактическая частота проходов при разных событиях и внешняя инициализация/сброс всех счётчиков; для них нужны отдельный анализ вызывающих путей и при необходимости измерения на безопасном стенде.

Продолжение 2026-09-30: [следующий проверенный срез](../charge-boundaries/REPORT_RU.md). Ограничения первоначального среза выше описывают его собственную область проверки.
