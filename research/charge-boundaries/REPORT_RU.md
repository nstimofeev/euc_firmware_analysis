# S22 2.37/2.41: границы переходов состояния зарядки 2 и приоритет внутри вызова

Проверены **56 полных вызовов оригинального Thumb** из расшифрованных образов: 28 сценариев на версию. Вызов начинается с входа автомата (`0x0801b3b4` / `0x0801b990`) и доходит до возврата после общего хвоста (`0x0801b9ae` / `0x0801bf8a`). RAM задаётся явно, MMIO отображена как инертная память. `evidence.json` хранит записи состояния с PC, MMIO-записи с PC, результат реальной функции процента, RAM и SHA-256 образов. Вызовов внешнего стаба **нет**: потребитель процента исполняет `0x0801785c` в 2.37 и `0x08017450` в 2.41. Это исследование дополняет `research/charge-states/REPORT_RU.md`, где эти границы и перезапись 2→20 были открытыми вопросами.

## Проверенные границы

Все пороги счётчиков проверяются по **старому** `u32`: значение на единицу ниже только увеличивается и оставляет state=2, значение на пороге выполняет переход. Для напряжения используются signed `int32`, для тока signed `int16`; показанные числовые значения — значения полей RAM, физические единицы здесь не установлены. Адрес state — `0x2000066c`.

| Переход | Условие и проверенные граничные пары | PC записи state, 2.37 / 2.41 |
|---|---|---|
| 2→3 | `BatState=1`, `TotalVoltage>0x30ed` (12525), счётчик `0x2000064c≥270500`: 270499→270500 без перехода; 270500→3. Напряжение ровно 12525 не переводит и уменьшает счётчик на 10, если он >10. | `0x0801b692` / `0x0801bc6e` |
| 2→4 | `BatState=1`, `TotalVoltage>0x3264` (12900), `0x20000650≥20`: 19→20 без перехода; 20→4. При напряжении ровно 12900 состояние остаётся 2 и счётчик 20→19. | `0x0801b6f6` / `0x0801bcd2` |
| 2→8 | `BatState=1` и либо `TotalVoltage>0x20000678` с результатом процента >100, либо результат процента > `u16[0x20000680]`, этот порог <100, а результат ≤100; `0x20000654≥20`. При результате 255 и первой ветке 19→20 без перехода, 20→8. Во второй ветке реальная функция возвращает 80: порог 79 даёт 8, порог 80 не даёт 8 (счётчик 20→19). | `0x0801b778` / `0x0801bd54` |
| 2→9, первая проверка | Входной байт `0x20003158` / `0x2000315a` >10, `0x20000658≥50`: 49→50 без перехода, 50→9 с `0x20000685←1`. | `0x0801b83c` / `0x0801be18` |
| 2→9, вторая проверка | Входной байт `0x20003159` / `0x2000315b` >10, signed `0x20000646>600`, `0x2000065c≥200`: 199→200 без перехода, 200→9 с `0x20000686←1`. При токе ровно 600 перехода нет и счётчик 200→199. | `0x0801b89c` / `0x0801be78` |
| Входной 2→5 | Только при `0x20000648=1`: `signed16((ADC[0x200034fe]>>4 - zero[0x2000064a])*17)>12000`, `0x20000660≥50`. При zero=1000 и ADC>>4=1705 получено 11985, 50→49 без перехода; при 1706 получено 12002, 49→50 без перехода, а старое 50 даёт state=5. | `0x0801b434` / `0x0801ba10` |

Для 2→8 отношение вычислено **оригинальным кодом**: ненулевой флаг `base+2` приводит к 255, а нулевые флаги и числители 80 при знаменателях 100 к 80; base `0x20004ba4` (2.37) / `0x20004e24` (2.41). Оба результата записаны как `percent_r0` при возвращении из функции. В случаях 2→3/4 с `BatState=1` реальные вызовы функции процента не нужны, если более ранняя ветка завершает диспетчер; в остальных случаях она также исполняется с контролируемыми RAM-полями. Никакая интерпретация 255 как физического процента не требуется: это sentinel при флаге входных данных.

## Приоритет и общий хвост

При спаде BMS-бита после сохранённой защёлки=1 ветка состояния 2 обнуляет `u16[0x20000670]`, вызывает set-помощник и пишет 20 в state (`0x0801b596` / `0x0801bb72`). Но диспетчер **не прекращает вызов**: условия state-2 далее проверяются без повторного чтения state. Пары записей в одном вызове подтвердили `20→6`, `20→3`, `20→4`, `20→8`, `20→9` для обоих образов. Например, при напряжении 12526 и старом `0x2000064c=270500` в 2.37 наблюдаются записи `(0x0801b596,20)`, `(0x0801b692,3)`; в 2.41 `(0x0801bb72,20)`, `(0x0801bc6e,3)`. Если последующие условия не выполнены, state остаётся 20. При спаде обоих BMS-битов state=20 пишется дважды и set-помощник вызывается дважды. Первые ветки 2→6/3/4/8 после успеха уходят к хвосту, поэтому не достигают поздних 2→9 в этом вызове.

Два поздних условия 2→9 независимы друг от друга и **оба могут сработать в одном вызове**: дважды пишется state=9, обе защёлки `0x20000685/86` становятся 1, наблюдаются две пары записей `0x422101b0←1` и set-помощника. Входной блок 2→5 расположен перед диспетчером: при его срабатывании и подготовленной BMS-защёлке единственная запись state — 5, ветка state=2 вообще не исполняется в том вызове.

Все сценарии достигают общего хвоста. Его результат для проверенных флагов: 2→5 устанавливает `0x20000672=1` и бит 0x40 в `u16[0x200030de]`; 2→4 устанавливает `0x20000673=250` и бит 0x40; 2→8 устанавливает `0x20000684=250` и бит 0x80; первый 2→9 ставит бит 0x100 в `0x200030de`, второй — бит 0 в `u16[0x200030e0]`. Дополнительный тест с `BatState=0`, первым 2→9 и счётчиками хвоста за порогом наблюдает сначала `0x422101b0←1`, затем **`←0` в том же вызове** (`0x0801bb0e` / `0x0801c0ea`). Поэтому запись bit-band при переходе не даёт безусловного заключения о конечном состоянии физической линии.

## Метод и пределы

Команда из корня репозитория:

```bash
python research/charge-boundaries/emulate_boundaries.py
```

Входы SHA-256: 2.37 `d98e8302df3a331660e5ff76be0e828608aee88ae57d0c25147d8b2a314ad904`; 2.41 `99491754f5478caf5d97a5fa31c0a17bc7be55f0c14ee3f87058b55916fe9509`. Скрипт перезаписывает только `research/charge-boundaries/evidence.json`. Каждый случай создаёт новую Unicorn-машину с исходным образом и инициализированной RAM, затем задаёт указанные входы. Периферия и bit-band отображены как инертная память, без электрического поведения и без аппаратного alias-эффекта. Длительность удержания условий в секундах, внешние писатели счётчиков и назначение MMIO-выводов не определяются этими тестами. Отдельные значения полей в искусственных сценариях проверяют локальную достижимость веток, а не реальную совместную достижимость таких входов на колесе.
